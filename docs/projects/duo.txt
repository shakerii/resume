Response:

Ramtin, I would design this as an adaptive, AI-generated language learning platform, rather than a traditional course-based app like Duolingo.

The most important architectural decision is this: your app should model a learner's skills and knowledge gaps, not just their progress through a curriculum.

That decision affects almost everything: how you generate content, how you reuse cards, how you score answers, how you schedule reviews, and how you decide what the user should learn next.

Your stack — React, Next.js, TypeScript, tRPC, Prisma — is a good fit. I would start with a modular monolith, a relational database, a background job system for AI generation and reminders, and an adaptive learning engine that can evolve as you collect real user data.

# 1. The core product model

## Learner Profile

Languages · Goals · Interests · Available time

Skill Model

Vocabulary, grammar, fluency, comprehension, pronunciation and other individual skills.

Learning Goals

IELTS, TOEFL, professional English, meetings, socializing and more.

Adaptive Learning Engine

Select existing cards · Identify gaps · Generate new cards · Schedule reviews

Card-Based Learning

Answer · Receive feedback · Get a multidimensional score

Memory & Review System

Estimate retention · Schedule reviews · Update skill estimates

The system should operate as a feedback loop:

1. Estimate what the learner knows.

2. Identify their highest-value knowledge gaps.

3. Find an existing card that targets a gap, or generate a new one.

4. Evaluate the answer at a finer level than correct or incorrect.

5. Update the learner's skill estimates and memory state.

6. Schedule future reviews and choose the next activity.

This is the central system to build around.

# 2. The biggest design decisions

I'd establish these principles before designing your database.

A. Skills are independent of levels

A learner can have excellent reading comprehension, weak listening comprehension, and moderate speaking fluency simultaneously. Don't force those skills into a single A1–C2 ladder.

Use a level from 1–10 as a difficulty attribute of a card or task, not as a global user rank.

B. Separate reusable content from learner progress

A card is a reusable learning resource. A learner's attempts, mastery, due date and personal notes belong to separate records.

This allows thousands of learners to use the same card without duplicating its content or learning history.

C. Model individual skills, not just cards

One card can train several skills, and one skill can be trained by many different cards. A weak answer to a listening question shouldn't automatically mean the learner has weak grammar.

D. AI generates structured content, not arbitrary lessons

The model should generate validated card payloads tied to explicit skills, language variants, difficulty, context and evaluation criteria. Your application should own scheduling, identity, deduplication and learner state.

E. Score multiple dimensions

A single score is convenient for the interface, but your learning engine needs more detail: accuracy, grammar, vocabulary, fluency, comprehension, pronunciation and task completion where applicable.

### Prisma implementation notes

I would use PostgreSQL and Prisma for the core data model.

* Use enums for stable internal states, such as `PENDING`, `PROCESSING`, `PUBLISHED` and `FAILED`.

* Use relational tables for searchable taxonomies and skill mappings.

* Use JSON fields for heterogeneous card payloads and detailed score breakdowns.

* Use immutable card versions so changing an answer key does not silently alter the meaning of historical attempts.

* Add explicit language codes, preferably BCP 47-compatible values, instead of assuming that every language has only one locale.

* Use transactions when recording an attempt and updating its learning state.

* Use unique constraints and idempotency keys to prevent duplicated jobs or attempts.

For card payloads, TypeScript types alone are not enough: validate AI output at runtime using a schema validator such as Zod before writing it to PostgreSQL.


# 5. Card architecture: a common envelope, different payloads

This is one of the most important implementation choices.

Don't create a separate database table for every card type. Instead, use a common `Card` model with a discriminated payload, then build a separate renderer and evaluator for each supported type.

## Common card model

Every card should have:

* A stable ID and one or more immutable versions.

* A target language and, where relevant, a source language.

* One primary learning objective and optional secondary objectives.

* Skill, topic, exam-track and difficulty metadata.

* A card type and a structured payload.

* An answer evaluation strategy.

* Optional media, hints and explanations.

* Provenance and quality status.

Here's how a TypeScript model could look:

TypeScript

```
import { z } from "zod";

const BaseCardSchema = z.object({
  schemaVersion: z.number().int().positive(),
  prompt: z.string().min(1),
  instructions: z.string().optional(),
  explanation: z.string().optional(),
  hint: z.string().optional(),
});

const MultipleChoiceSchema = BaseCardSchema.extend({
  type: z.literal("MULTIPLE_CHOICE"),
  options: z.array(
    z.object({
      id: z.string(),
      text: z.string(),
    })
  ).min(2),
  correctOptionIds: z.array(z.string()).min(1),
});

const FillGapSchema = BaseCardSchema.extend({
  type: z.literal("FILL_GAP"),
  sentence: z.string(),
  acceptedAnswers: z.array(z.string()).min(1),
});

const ShortAnswerSchema = BaseCardSchema.extend({
  type: z.literal("SHORT_ANSWER"),
  expectedAnswer: z.string(),
  acceptedAnswers: z.array(z.string()).default([]),
});

const SpeakingSchema = BaseCardSchema.extend({
  type: z.literal("SPEAKING"),
  prompt: z.string(),
  evaluationCriteria: z.array(z.object({
    skillId: z.string(),
    weight: z.number().min(0).max(1),
  })),
});

const CardPayloadSchema = z.discriminatedUnion("type", [
  MultipleChoiceSchema,
  FillGapSchema,
  ShortAnswerSchema,
  SpeakingSchema,
]);

type CardPayload = z.infer<typeof CardPayloadSchema>;
```

This is a starting point, not the entire production schema. Reading and listening cards can use their own payloads or compose shared passage and audio resources with question payloads.

For production, add validation that option IDs are unique, correct-option IDs exist, answer keys are not exposed to the client before submission, and weights sum to an expected value.

# 6. How to model skills without a level ladder

You want to avoid the assumption that a person is globally beginner, intermediate or advanced.

I agree with the underlying design goal: mastery should be represented at the level of individual skills and learning objectives.

But I'd make one distinction: a card's difficulty, a user's mastery and a user's confidence are three different things.

For example, a learner might have the following profile:

## Example learner profile

English · Professional communication

Reading comprehension

84%

Technical vocabulary

78%

Grammar accuracy

57%

Listening comprehension

43%

Speaking fluency

36%

Pronunciation

62%

Illustrative mastery estimates only; not standardized proficiency scores or calibrated predictions.

These estimates let the engine recommend a challenging listening exercise without forcing the learner to repeat easy reading lessons.

## A practical first mastery model

For each learner, target language and skill, maintain something like:

TypeScript

```
type UserSkillState = {
  userId: string;
  targetLanguage: string;
  skillId: string;

  masteryEstimate: number; // 0..1
  confidence: number;     // 0..1
  evidenceCount: number;

  lastPracticedAt: Date | null;
  updatedAt: Date;
};
```

Interpret the fields carefully:

* `masteryEstimate` is the system's current estimate of ability.

* `confidence` describes how much evidence supports that estimate.

* `evidenceCount` records how much relevant practice has occurred.

These are not interchangeable. A learner with a 0.75 mastery estimate based on two attempts should not necessarily be treated the same as someone with the same estimate based on 100 attempts across varied contexts.

A single running average is a reasonable prototype, but I would eventually move to a probabilistic or item-response-based model that accounts for question difficulty, guessing, uncertainty and the skill being tested.

Also, keep the underlying mastery estimate separate from the user-facing difficulty selector. A user can request harder content without the application falsely assuming that their mastery has increased.


# 7. Scoring: go beyond pass/fail

I'd use a two-layer scoring system:

1. Attempt assessment: how well did the learner perform on this particular answer?

2. Learning-state update: what does that answer tell us about the learner's underlying skills?

These should not be the same calculation.

## Example scoring rubric

For an open-ended speaking response, the evaluator might return:

Illustrative response score

# 72 / 100

Partially successful

Task completion

85

Grammar accuracy

70

Vocabulary

78

Fluency

65

Pronunciation

60

Example only. Actual criteria and weights should vary by task, and the displayed values require a real evaluation.

The overall score could be a weighted combination of relevant dimensions:

S=∑iwisi∑iwiS = \frac{\sum_i w_i s_i}{\sum_i w_i}S=∑iwi∑iwisi

where sis_isi is a dimension score and wiw_iwi is that task's criterion weight.

However, do not apply the same rubric to every card. A multiple-choice listening question doesn't need a fluency score, and a speaking exercise shouldn't receive a pronunciation score unless the task provides enough evidence to assess it.

### Recommended evaluation pipeline

1. Collect the response. Preserve the selected option, text, audio reference or other answer format.

2. Evaluate the answer. Use deterministic rules where possible; use a model or specialized speech service where necessary.

3. Validate the evaluation. Ensure scores are in range, required dimensions exist, and feedback is grounded in the response.

4. Store the score breakdown. Save the raw attempt and the evaluator/model version.

5. Update skill estimates. Use the relevant evidence, accounting for difficulty, guessing and assessment reliability.

6. Schedule the next review. Consider performance, uncertainty, prior reviews and the learner's goals.

An LLM evaluator should return structured data, for example:

TypeScript

```
type AttemptAssessment = {
  overallScore: number;
  dimensions: Array<{
    skillId: string;
    score: number;
    evidence: string[];
    feedback: string[];
  }>;
  accepted: boolean;
  confidence: number;
};
```

Use server-side validation to constrain scores to 0–100 and confidence to 0–1.

For language evaluation, confidence is particularly important. An automated evaluator may struggle with accents, speech recognition errors, multiple valid translations or culturally dependent interpretations. Low-confidence assessments should contribute less to mastery updates or be flagged for reassessment.

Important: an answer score of 80 does not mean the learner has 80% mastery. The first measures performance on one task; the second is an estimate accumulated from relevant evidence over time.

# 8. The reminder system: spaced repetition plus adaptive review

I would implement two separate concepts:

* Memory scheduling: when is the learner likely to benefit from reviewing this card again?

* Learning priority: how valuable is this card relative to everything else the learner could practice?

A card can be due for review but have low priority if it trains an irrelevant skill. Conversely, an urgent exam goal might justify introducing new content even when no reviews are due.

## A practical review policy

Use an initial rule-based scheduler. You can replace or improve it later with an established spaced-repetition algorithm.

# 9. AI content generation and deduplication

This is probably your most challenging subsystem. The solution is not simply to ask an LLM to generate 100 new cards and compare their text.

You need a content generation pipeline that first determines what the learner needs, searches for reusable content, and generates only when existing content is insufficient.

## Recommended generation pipeline

1. Identify a learning gap

Skill estimates, goals, recent attempts, upcoming reviews

2. Search existing cards

Exact match → metadata filters → semantic similarity

3. Is an appropriate card available?

Yes

Reuse the card

No

Generate a candidate

4. Validate and deduplicate

Schema validation, answer checks, similarity checks, quality evaluation

5. Publish and attach to learning

Store a reusable card; create learner-specific scheduling state separately

## Three levels of duplicate detection

1. Exact duplicates: Normalize text, compare hashes, and enforce unique constraints on stable generation identities where applicable.

2. Near duplicates: Compare normalized text, answer keys, question structure and language. This catches small rewrites of the same exercise.

3. Semantic duplicates: Use embeddings to identify different wording that tests essentially the same thing. Compare learning objective, intended answer, scenario and assessment purpose alongside semantic similarity.

PostgreSQL with `pgvector` is a practical option for embedding-based candidate retrieval. You don't need a separate vector database immediately.

However, semantic similarity alone is not sufficient. Two questions can be semantically similar while testing different skills, and two nearly identical sentences can be useful if one tests pronunciation and the other tests grammar.

Deduplication should therefore consider both content similarity and pedagogical equivalence.

## How to instruct the AI to generate new content

Don't send a vague instruction such as "Generate five English questions."

Give the model a structured generation context:

TypeScript

```
type GenerationContext = {
  targetLanguage: string;
  sourceLanguage?: string;

  examTracks: string[];
  topics: string[];
  skillIds: string[];
  objectiveIds: string[];

  difficulty: number;
  cardTypes: string[];

  learnerGaps: Array<{
    skillId: string;
    mastery: number;
    confidence: number;
  }>;

  recentCardSummaries: string[];
  excludedConcepts: string[];

  desiredNovelty: "LOW" | "MEDIUM" | "HIGH";
};
```

The generation prompt should explain:

* Which specific skill or objective needs practice.

* What content the learner has already encountered.

* Which recent scenarios or question patterns to avoid repeating.

* What level of linguistic complexity is appropriate.

* What counts as a valid answer and how it should be evaluated.

* Whether the new card should be exam-specific, professional, conversational or general.

* What makes the proposed card meaningfully different from existing cards.

Ask the model to return structured candidates, validate them using Zod, then run deduplication and quality checks before publication.

Don't rely on prompt instructions alone to prevent duplicates. The application must enforce the constraints.

## An important distinction: content identity vs. generation identity

I would introduce three concepts:

* `Card`: the stable identity of a reusable learning item.

* `CardVersion`: a particular published revision of that item.

* `GenerationJob`: a request to create or improve content.

A generation job can produce several candidates, and multiple generation jobs may discover the same underlying card. Your system should be able to reuse the existing card rather than create another one.

If content is generated for one user, do not automatically make it public to everyone. Add publication states, review requirements and provenance metadata so you can control quality and sharing.

# 10. How to choose the next card

You don't need a sophisticated machine-learning recommendation model on day one. Start with a deterministic priority function, log the decisions and refine it as you gather data.

For example:

P(c,u)=wgG+wrR+wtT+wdD+wnNP(c,u)= w_gG+w_rR+w_tT+w_dD+w_nNP(c,u)=wgG+wrR+wtT+wdD+wnN

Where:

* GGG: relevance to the learner's known skill gaps.

* RRR: review urgency or estimated forgetting risk.

* TTT: relevance to selected goals, such as IELTS or professional communication.

* DDD: suitability of the card's difficulty.

* NNN: novelty and diversity value.

The weights should be configurable, and the variables should be normalized before combining them.

You should also include constraints that are not merely scoring preferences:

* Due reviews may need to be completed before introducing new content.

* A user who wants speaking practice should not receive an entire session of multiple-choice questions.

* Repeated exposure to the same scenario should be limited.

* A low-confidence skill estimate may justify a diagnostic exercise rather than immediate remediation.

* Cards with failed quality checks must never enter the learner's queue.

Eventually, you can optimize this policy using observed retention, improvement and engagement. Avoid optimizing only for session length or immediate correctness: those metrics can reward easy, repetitive exercises rather than genuine learning.
